## Décisions techniques livrées

Le [pipeline de référence](../07-CATALOG-SYNC.md) décrit les algorithmes et commandes définitifs. Il utilise Node 24, TypeScript, Zod et deux dépendances de développement ajoutées, **`pg` 8.23.0** et **`@types/pg` 8.23.1**, fixées dans le manifest et le lockfile. Aucun runtime TypeScript supplémentaire, serveur permanent, scheduler ou source secondaire n'est ajouté.

La nouvelle migration [20260906155043_phase2_catalog_pipeline.sql](../../supabase/migrations/20260906155043_phase2_catalog_pipeline.sql) convertit les stamps scalaires en `TEXT[]`, avec préservation des valeurs existantes, et crée :

- `private.catalog_sync_runs` : version source, résultat et statistiques ;
- `private.catalog_overrides` : corrections de champs et de mappings, valeurs source/effectives, motif, état appliqué et dernier run ;
- `private.catalog_entity_keys` : aliases rares nécessaires aux cartes locales et variantes corrigées.

Les trois tables ont RLS explicite, aucune policy/grant API et aucun accès général au schéma privé, y compris pour `service_role`. Aucun helper `SECURITY DEFINER` ni RPC supplémentaire. Les migrations Phase 1 restent strictement inchangées. Les types publics ont été régénérés par la CLI.

Identité : `v1:` suivi du JSON `[type, subtype|null, standard, stamps triés, foil|null]`. Disponibilité, label et tiers n'y participent pas. L'ID détaillé upstream est conservé séparément ; les variantes legacy ne reçoivent jamais `generated`.

Ordre : rang naturel intra-set, puis familles Normal/Holo/Reverse/autres et foils/stamps ; Poké Ball avant Master Ball. Pokémon ajoute la date en priorité, avec NULL en dernier. Les dates suivent carte, produit fiable, set FR/global puis priorité finale d'un override.

Hash de cible : SHA-256 du JSON compact de la liste ordonnée des IDs internes de variantes **en chaînes décimales**. Version initiale 1, incrément seulement si la séquence change. Les métadonnées descriptives seules ne produisent pas de version.

Les overrides sont des tableaux JSON stricts, validés avant écriture, avec six actions et provenance. Ils permettent noms, images, dates, disponibilité, propriétés de variantes, activité, carte/variante locale et mappings include/exclude. Les doublons, conflits, cibles inconnues et clés incohérentes sont refusés. Les patches préservent chaque propriété omise ; les redondances sont signalées sans suppression automatique. Les exemples du [guide des corrections](../../data/catalog-overrides/README.md) sont synthétiques et ne sont pas chargés.

Les IDs sont préservés, les disparitions désactivées et les lignes conservées. L'apply groupe catalogue, mappings, overrides, aliases et états dans une transaction, avec lots de 1 000 lignes. Le dry-run est une transaction en lecture seule, y compris pour les séquences. Les réservations d'IDs sont vérifiées à l'apply ; une erreur peut laisser un trou de séquence PostgreSQL, mais pas un catalogue partiel. Toutes les bases distantes sont refusées.
